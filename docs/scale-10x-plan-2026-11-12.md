# 10 倍流量方案（2026-11-12）

目标：按 **2026-11-11 的 10 倍**承载——每天 130 万请求、峰值每秒 40 请求、**同时在途约 800 条**（昨天峰值小时 14,673 请求、平均在途 81 条、平均时长 20 秒、88% 流式、平均提示 17.6 万 token）。
本文基于当天实测，写明每一层现在的上限、10 倍时的需求、改法、顺序和代价。先说结论，再逐层展开。

## 0. 结论

1. **网关单进程是第一道墙，而且已经贴着了。** 实测每个请求消耗网关 **0.16 秒 CPU**（切换后 1779 秒内 2408 个请求用了 394 秒 CPU）。单线程上限约每秒 6 个请求 = 昨天峰值的 1.5 倍。10 倍需要 6–7 个核的网关算力 → 必须多进程，同时把每请求 CPU 至少砍一半。
2. **控制台是第二道墙。** 每请求 0.084 秒 CPU（所有 worker 隧道流量经它中转），10 倍需要 3.5 个核 → 也要多进程或改隧道拓扑。
3. **账号是第三道墙，也是最贵的。** 昨天 1 倍峰值时已经出现 980 条 `team_capacity_exhausted`（组织里没有可调度账号），说明峰值时账号池已经用满。10 倍大致需要 **2500–3300 个账号、25–30 台节点、≥50 个组织**。
4. **数据库不是第一道墙，但 10 倍时必须换。** SQLite 同步调用阻塞事件循环、单写者、`usage_logs` 每月涨 20 GB；多进程网关需要多写者，热备需要复制——终局是 PostgreSQL。
5. **顺序**：先给网关减负 + 多进程（2–3 周，先解燃眉），同时开始账号/节点扩容（持续，钱）；再迁 PostgreSQL（3–4 周）；监控贯穿全程。软件侧 6–8 周可到位；账号供给决定实际到 10 倍的时间。

## 2. 网关：减负 + 多进程（第 1–3 周）

### 2.1 为什么每请求 0.16 秒 CPU

未做剖析前的判断（需要一次 CPU 采样确认，见 §6）：请求体平均 17.6 万 token ≈ 700 KB JSON，每条要 解析 → 形态判定（cc-shape）→ 指纹/哈希 → 历史比对（echo/prefix）→ 渲染导入文本 → 再序列化发给节点；回程 20 秒的 SSE 逐事件翻译；外加每请求十几行日志（usage ledger、cc-shape、team-pick 等）写 journald。这些都在一个线程上。

### 2.2 减负（目标：CPU/请求 ≤ 0.08 s）

- 先做一次 12 秒 CPU 采样拿到真实热点（§6），按热点改，不猜。
- 可预见的项：请求体只解析一次、历史比对只在需要时做；日志降噪（usage ledger 一行汇总、cc-shape 只在判定变化时打）；SSE 翻译减少字符串拼接。
- 全局在途上限 `GATEWAY_MAX_INFLIGHT`（按进程）：超出直接 503/429 快速拒绝，而不是接进来排队、最后全部 499。这是"过载时有序降级"，今天没有它才会全站停摆。

### 2.3 多进程

- **拓扑**：每个蓝/绿组从 1 个进程变成 N 个进程（8400–8407 / 8402… 一组端口），nginx `upstream` 用 **一致性哈希按 API key**（`hash $http_authorization consistent`）分发，保证同一个 key / 同一条对话总落在同一个进程。
- **为什么按 key 哈希**：网关的进程内状态都以 key 或对话为粒度——粘性会话、X-69 停靠轮次、每用户限流窗口、每用户在途计数——按 key 分片后这些状态不需要外移。
- **必须外移的状态**（跨 key 共享）：账号级在途数（`AccountGates.inFlight`）、账号认证失败计数（`AuthFailureTracker`）、账号 RPM。现有 `gateway_account_leases` / `gateway_account_hits` 表已经是 DB 共享的雏形，补齐即可；认证失败计数放进 DB 还顺带解决"网关切换计数归零"的老问题。
- **蓝/绿切换**脚本改为按组切换；看门狗按组探测。
- **主服务器**：先垂直升级到 16 核 32 GB（最便宜、最快），N=8。
- 产出：网关可用算力 ×8，叠加减负后 ×16 以上，10 倍够。

## 3. 控制台：拆出隧道中转（第 2–4 周）

控制台现在同时做三件事：管理 API、节点注册/心跳、**所有 worker 隧道的字节中转**。第三件占了它的 CPU。

- 把隧道中转拆成独立进程组（`1dayapi-relay@N`），节点连接时按节点 id 哈希到固定的中转进程；网关向控制台查"这个节点在哪个中转"后直连该中转。管理 API 和心跳留在原进程，重启管理台不再切断在途隧道（今天每次控制台重启都是十几条 5xx）。
- 中间态（更快，1 周）：先把管理 API 从中转进程里分出去，让中转进程只做中转；多进程留到 PostgreSQL 之后。

## 4. 数据库：PostgreSQL（第 3–7 周）

### 4.1 为什么必须换

- `node:sqlite` 是同步 API，389 处调用（`one` 61、`all` 16、`run` 255、`tx` 57）全部阻塞事件循环。X-71 事故本质就是这个。
- 单写者：网关多进程后 8 个进程 + 控制台 + 中转同写一个文件，`busy_timeout` 排队会变成常态。
- 热备：SQLite 只能用 Litestream 做秒级异步副本；PostgreSQL 流复制是现成的、可读的从库。
- 体量：10 倍后 `usage_logs` 每月 +20 GB，索引比数据还大；PostgreSQL 按月分区 + 归档是成熟做法。

### 4.2 怎么迁

1. **先盘点**（1 周，不动生产）：按 57 个 `tx` 列出每个事务跨哪些表、哪些查询会随行数线性变慢（组织日用量、用户统计、缓存退款扫描）、哪些读可以走从库。
2. **新 `core/db`**：`pg` 连接池，`one/all/run` 变 async，`tx` 变 `async (client) => …`；每个调用点加 `await`，TypeScript 会把漏掉的地方报出来。
3. **双写过渡**：结算日志（settlement journal）已经是异步队列，先让 `usage_logs` 走它写 PostgreSQL，SQLite 继续写；对比一周数据一致后切读。
4. **一次性迁移小表**（accounts/users/api_keys/…，几万行，几分钟）：选低峰停写 5 分钟完成。
5. **分区与保留**：`usage_logs` 按月分区，热数据 3 个月，老分区转冷存；组织/用户的"今日用量"改为计数表增量维护，不再 SUM 原表。
6. **热备**：第二台机器跑流复制从库 + 一套 nginx/网关/控制台（不接流量），Cloudflare 切源即可接管；RPO 秒级，RTO 分钟级。

机器：PostgreSQL 主库放主服务器（16 核 32 GB 够），从库 8 核 16 GB（你要买的热备机按这个配）。

### 4.3 过渡期的 SQLite 止血（第 1 周就做）

归档 30 天以上的 `usage_logs` 到独立文件（主库瘦身 70%）；组织/用户日用量预聚合；慢查询加耗时日志。迁移前这些都要，迁移后计数表直接复用。

## 5. 供给：账号、节点、代理、组织（持续）

这是 10 倍里**最贵、最慢、风险最大**的一层，软件做完也要等它。

- **账号**：昨天峰值 330 个已耗尽（980 条 503），10 倍按 8–10 倍账号估：2500–3300 个。上号产能是瓶颈（camoufox 工具 + 人工），需要给出每周能上多少的实际数字再排期。
- **组织**：现在 9 个组织，单组织上百账号。上游按组织处置（已出现过组织级封禁告警），10 倍时**每组织不超过 50 个账号、≥50 个组织**，把爆炸半径压住。
- **节点**：按现在 94 GB 机器挂 100 账号、名义 252 会话的密度，需要 25–30 台。每台用现有加节点脚本（worker-03 的流程）半天可上。每台要过设备身份检查。
- **代理**：一账号一代理不变，3000 条；代理池健康检查和 `proxy_down` 处置要自动化，人工跟不上。
- **上游风险**：规模越大越显眼。坚持 TUI 入口、第三方流量不走直连、Tokway 式"换 token 直转"不做；第三方回落（`-p`）比例要监控并压低。这一层出事是封号潮，软件层解决不了。

## 6. 监控与演练（贯穿）

- **指标采集**：每个网关/中转进程的 `/internal/metrics` 由 Prometheus（或 VictoriaMetrics）抓取；Grafana 看板：请求率、499/5xx 率、首字节 p50/p99、事件循环 p99、在途数、账号池可调度数、组织窗口用量、节点会话数/内存。
- **告警**（替代今天"客户来报"）：事件循环 p99 > 1 s、499 比例 > 10%、5xx > 2%、可调度账号 < 阈值、某组织被封、节点离线、磁盘/库体积。看门狗自动切换已上线。
- **集中日志**：journald 单机保留 4 小时，10 倍后更短。Loki 或至少 rsyslog 汇聚到一台机器，保留 7 天。
- **CPU 采样常态化**：网关启动参数预留 `--cpu-prof` 开关，或保留 inspector 采样脚本；每次大改前后各采一次。今天那次采样被权限拦住，需要你同意一次，之后写进发布流程。
- **压测**：用 fake-claude 节点 + 回放昨天的请求体（去标识）在蓝组压到 40/s，看网关 CPU、事件循环、DB 写入；这是判断"10 倍是否真的到位"的唯一客观办法。
- **故障演练**：每月一次：杀网关进程（看门狗切换）、停主库（从库接管）、断一台节点。

## 7. 排期与代价

| 周 | 做什么 | 产出 |
|---|---|---|
| 1 | CPU 采样 → 网关减负第一批；全局在途上限；SQLite 归档 + 预聚合；Kevin 等大户限流；PostgreSQL 调用点盘点；Prometheus/Grafana 搭起来 | 网关单进程上限 ~12/s（3 倍）；过载有序降级；看得见 |
| 2–3 | 网关多进程（按 key 哈希、账号级状态外移、蓝绿按组）；主服务器升 16 核；控制台拆管理 API | 网关 ×8；控制台重启不断隧道 |
| 3–7 | PostgreSQL：新 db 层 → 双写 → 切读 → 小表迁移 → 分区；热备机上从库 | 异步查询、多写者、热备、体量可控 |
| 4–6 | 隧道中转多进程 | 控制台 ×N |
| 持续 | 账号 → 3000、组织 → 50+、节点 → 25–30、代理 → 3000；每周报产能 | 真正的 10 倍 |

机器（粗估，按 Contabo 价位）：主服务器 16 核 32 GB ≈ 现在的 2 倍价；热备/从库 8 核 16 GB 一台；节点 25–30 台 × 现有规格。账号和代理的成本按你的采购价算，是大头。

## 8. 风险与边界

- 网关多进程把"进程内状态"的假设全部翻一遍，漏一个就是跨进程不一致（如同一账号被两个进程同时超并发）。靠 e2e 多进程用例 + 压测兜底。
- PostgreSQL 迁移期间不能停发布，双写期数据对账要有脚本。
- 供给跟不上时，软件先到位也只能到账号允许的倍数；要以"每周上号数"倒推可承诺的时间。
- 上游处置是最大外部风险；多组织、小组织是唯一可控的缓解。

## 9. 需要你决定的

1. 同意一次网关 CPU 采样（12 秒，inspector，采完关端口）——减负从它开始。
2. 主服务器升配时间（需要一次整机迁移或停机 ~10 分钟）。
3. 热备机配置改为 PostgreSQL 从库规格（8 核 16 GB）。
4. 账号/代理/节点的采购节奏和上号产能数字。
5. 大户限流：Kevin 的 key 要不要先设每分钟上限。
